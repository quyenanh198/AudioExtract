Token bucket + 100 req/phút/user + 429 kèm Retry-After là combo hợp lý và đúng chuẩn — cho phép burst tự nhiên thay vì chặn cứng theo cửa sổ cố định, và Retry-After giúp client tự backoff đúng semantics HTTP thay vì đoán mò retry. Chọn thuật toán này không sai.

Nhưng câu "gần như best practice chuẩn, không có gì đặc biệt custom" mới là chỗ tôi lo, vì phần khó của rate limiting hiếm khi nằm ở chọn thuật toán — nó nằm ở nơi lưu trạng thái và cách định danh "user", mà hai chỗ đó gần như luôn phải custom cho hệ thống cụ thể của bạn:

- **State lưu ở đâu?** Nếu API chạy nhiều instance (mà API public thường phải scale), token bucket giữ in-memory ở từng instance sẽ cho user thực đạt N×100 req/phút thay vì 100, với N là số instance. Nếu dùng store chung (Redis...), thao tác đọc-trừ-ghi token phải atomic (Lua script hoặc lệnh nguyên tử), không thì hai request đồng thời có thể cùng đọc thấy còn token và cùng lọt qua — limit thực tế lỏng hơn công bố đúng lúc traffic cao, tức đúng lúc bạn cần nó chặt nhất.
- **"User" được định danh bằng gì?** Với API public, nhiều khả năng có cả traffic chưa auth, lúc đó "user" thực chất là IP. IP sau NAT/proxy công ty hay mobile carrier có thể là hàng trăm người dùng thật chia sẻ — họ chặn lẫn nhau dù không ai vi phạm; ngược lại kẻ muốn lạm dụng chỉ cần xoay IP là né được giới hạn hoàn toàn.
- **Retry-After tính thế nào?** Token bucket cho phép burst nên "khi nào có token tiếp theo" phụ thuộc tốc độ refill, không phải hằng số. Nếu set cứng 60s cho mọi 429, một loạt client bị chặn cùng lúc sẽ retry đồng loạt sau đúng 60s — tạo thundering herd ngay sau khi cửa sổ mở lại.

Một hướng khác đáng cân nhắc: thay vì tự build token bucket + store chung từ đầu, dùng rate limiter đã có sẵn ở tầng gateway (Cloudflare, API Gateway, nginx `limit_req`, Envoy...) — những chỗ này đã giải quyết distributed state, atomicity và tính Retry-After chính xác, được production-test ở quy mô lớn hơn nhiều so với code tự viết. Nếu vẫn muốn tự implement, GCRA (leaky bucket biến thể) thường dễ tính Retry-After chính xác hơn token bucket thuần và tránh cho phép burst full 100 request dồn cùng một khoảnh khắc.

Nếu bỏ qua mấy điểm trên, rủi ro cụ thể là: rate limiter "trông như hoạt động đúng" khi bạn test với 1 instance hoặc traffic thấp, nhưng khi scale ngang hoặc traffic spike thật, limit thực tế bị vượt vài lần mà không ai phát hiện — cho tới khi DB hoặc dịch vụ downstream quá tải. Lúc đó incident xảy ra đúng giờ cao điểm, và khó debug vì rate limiter vẫn "báo cáo" đang chặn đúng 100/phút mỗi instance.

Vài câu hỏi để tự kiểm tra trước khi code: API sẽ chạy bao nhiêu instance, và bucket state định lưu ở đâu — in-memory hay store dùng chung? Với request chưa auth, "user" sẽ được định danh bằng gì (IP, API key, session)? Và bạn đã thử test concurrent (nhiều request bắn đồng thời) để xem limit thực tế có đúng 100/phút không, hay mới test tuần tự?
